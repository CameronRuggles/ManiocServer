## Gate 1 — Podman + runsc, socket-served onion site (IN PROGRESS)
Environment constraints discovered (all properties of this nested sandbox VM, to be re-verified on the Stage 1 rig — none are design findings yet):
- **All public container registries unreachable** (docker.io, quay.io, ghcr.io, public.ecr.aws: TLS handshake timeouts through the sandbox proxy). Images must be built locally — which happens to be the production approach anyway (v3 A6: local build + `podman import`, no registry parsing). First local attempt (dpkg-deb extraction of the apt download-only closure) produced an incomplete rootfs: apt skipped already-host-installed packages (dash, libc6), so the image had no shell/libc. Switched to **mmdebstrap --mode=chrootless** (the design's own builder) for a correct closure.
- **Podman storage**: overlay driver unusable (overlay mounts denied; fuse-overlayfs has no fuse device). `vfs` driver on the 100 GB workspace volume works.
- **setns(2) is hard-blocked** in this sandbox — even `nsenter` onto our own netns fails, and netavark fails identically under crun. Podman-managed containers therefore struggle: crun works for --network=host (it skips the join) but **runsc always attempts a netns join when driven by podman and dies at `start`** ("joining net namespace /proc/<pid>/ns/net: operation not permitted"). A spec-editing shim (scripts/runsc-shim.py: strips the network namespace from config.json, forces --ignore-cgroups, --network=none for nginx / --network=host for tor) did NOT cure the start-time join — runsc resolves a netns from its caller regardless.
- Counter-evidence: **standalone `runsc run` on a hand-built OCI bundle got past sandbox creation** (failed later only on the broken rootfs's missing /bin/sh). So gVisor itself runs fine here; the blocked seam is specifically podman→runsc namespace handoff under this sandbox's seccomp policy.

## Gate 1 — sub-item verdicts (rootful route, executed via standalone runsc bundles; podman harness blocked by sandbox, see above)
Execution vehicle note: because podman→any-runtime container networking dies on this sandbox's setns block, the stack was run as **standalone OCI bundles under runsc directly** (bundle-web/, bundle-tor/, specs generated by `runsc spec`). This tests the same runtime, same images (locally built poc-base, 67 MB, tor+nginx from apt closure — scripts/build-base-image-v2.sh), same config semantics. The podman/Quadlet management layer remains untested HERE and is a Stage 1 rig item — **the A5 engine data clause is therefore NOT settled by this run** (neither rootful-podman nor the rootless comparison could be exercised; both hit the same setns wall).

1. **Socket creation under runsc (the Appendix B question): PASS — with a required flag.** With default settings, nginx inside gVisor created the socket only *inside* the sandbox (gofer-emulated; invisible on the host). With **`runsc --host-uds=create`**, the socket appeared as a real file in the host shared directory (`srw-rw-rw- shared-web/http.sock`) and nginx served through it. Design consequence: **--host-uds=create (or all) is a REQUIRED, non-default runsc flag for B** — this must be baked into the golden config and the probe checks, because its absence fails *silently* (site looks up inside B, tor gets nothing). This is the single most valuable finding of the PoC.
2. **B has no network: PASS.** Inside B (runsc --network=none): /proc/net/dev shows ONLY `lo`; /proc/net/route is empty (no routes at all); /proc/net/tcp has zero listeners; the onion key directory does not exist in B's filesystem view (/var/lib/tor/hs absent). (Log: logs/gate1-b-isolation.txt. dash lacks /dev/tcp so connect-probes were moot — with no non-loopback interface and no routes, egress is impossible by construction.)
3. **A (tor) under runsc: PARTIAL.** Tor 0.4.9.11 inside runsc started cleanly, accepted the full golden torrc (all PoW/intro-DoS/MaxStreams options live, not just validated), created its DataDirectory on the bind-mounted volume and generated a v3 onion identity (w6m5ei5q…onion, throwaway). It could NOT bootstrap: —network=sandbox dies on the setns block; —network=host gives the sentry a stack whose TCP connects hang (verified independently with a curl diagnostic bundle: connect() never completes), while host processes reach Tor relays fine (4/4 directory authorities OPEN on direct TCP). Verdict: gVisor egress networking is inoperable inside this outer sandbox — an environment limitation, evidenced, not a design failure. **Re-test A-under-gVisor egress on the Stage 1 rig** (real KVM host) before alpha.
4. **Page loads over Tor (end-to-end): PASS (with A substituted by a host tor process).** To complete the runbook's headline criterion despite (3), tor was run as a host process with the identical golden torrc (HiddenServicePort 80 unix:…/shared-web/http.sock) serving B's socket. It bootstrapped 100%, published, and the page was fetched through the real Tor network via a separate client tor: `curl --socks5-hostname … http://tz475vfnspdeltxmz5dtccjcq5xgcef5ttdbb3l2dfymmlpmsgsye5ad.onion/` → the Gate 1 page (fetch succeeded on attempt 4 during descriptor propagation, then reproducibly; log: logs/gate1-fetch-over-tor.txt). So the complete chain **Tor → unix socket → nginx-in-gVisor-with-no-network** works end to end; the only substituted link is A's sandbox, for the reason in (3).
5. **No host TCP listener for the website: PASS.** `ss -ltn` shows no web listener (only the test client's local SOCKS port). The site exists on the host solely as a unix socket file.
6. **B restart resilience: PASS (informal).** B was killed and restarted repeatedly during debugging; nginx recreated the same socket path cleanly each time with no manual cleanup, and the final over-Tor fetch ran against a restarted B.
7. **Ceilings (fork-bomb/memory) under runsc: NOT TESTABLE here.** --ignore-cgroups is forced by the sandbox (Gate 0 caveat); per DQ2 that likely disables runsc's cgroup ceilings in this environment, so any result would be meaningless. Deferred to Stage 1 rig, explicitly.
8. **Rootless comparison: NOT RUN.** Same setns wall applies a fortiori; no signal available in this environment. A5 decision remains open pending Stage 1.
9. **Deviations recorded (PoC-only, not design changes):** shared socket dir mode 777 (production: setgid 2770 + group, per delta review); nginx workers run as root in-sandbox because the outer sandbox denies chown (worker initgroups failed against unmapped uids); tor ran as root inside its sandbox; local image assembled from Ubuntu 24.04 packages (production: Debian 13 via mmdebstrap --mode=unshare — mmdebstrap itself was tried here and failed on chrootless-mode maintainer-script errors and /tmp size; unshare mode should be used on the rig).

## Configuration change baked in before tranche-2 tests
- **Golden B/runsc invocation now requires `--host-uds=create`.** Added `configs/runsc.golden` as the canonical PoC invocation record: B is launched with `--network=none --host-uds=create`. ## Gate 1b — Rotation — **PASS**
Method: two standalone-runsc B bundles (`bundle-web-b1`, `bundle-web-b2`) sharing one host socket directory (`shared-rotation/`); each nginx listens on its own socket (`b1.sock`/`b2.sock`); host tor (A, substituted as in tranche 1) targets the fixed path `http.sock`, a host-owned symlink. Scripts: `scripts/build-rotation-bundles.sh`, `scripts/gate1b-swap.sh`, `scripts/gate1b-cycle2.sh`, `scripts/gate1b-fallback.sh`. Logs: `logs/gate1b-swap.txt`, `logs/gate1b-cycle2.txt`, `logs/gate1b-fallback.txt`.
- **Symlink swap (primary mechanism): PASS.** B2 started on the idle socket and answered a health request through it (`B2`). The symlink was atomically replaced (`os.replace` of a fresh symlink over `http.sock`). All 6 post-swap requests over Tor returned **B2**, 0 failures; runsc/gVisor follows the host-side rename — the A8 fallback was not needed for the primary path. Pre-swap requests returned B1 as expected.
- **Graceful drain: PASS (both cycles).** Cycle 2 used an unlimited in-flight Tor download of a 30 MiB file from B2, swapped the symlink to B1 (new requests: B1, 0 failures), then gave B2 SIGQUIT. The download grew from 8,790,016 bytes at QUIT to 14,327,808 / 20,856,832 / 27,484,160 bytes at 10 s samples and **completed at 40 s** (31,457,280 bytes, curl exit 0), after which B2 was stopped — the old worker finished its existing stream while taking no new ones, exactly the A8 semantics.
- **60 s drain cap: PASS (cycle 1, as designed).** Cycle 1's in-flight 200 MiB download (client-side `--limit-rate 1M` to keep it in flight) grew 3,805,184 bytes at 10 s → 19,959,808 after the swap → 35,155,968 during drain → 58,478,592 at the 60 s cap, with B1 still running; B1 was then force-stopped and the transfer closed (final 59,047,936 bytes, curl exit 18). This is the specified behaviour (over-long downloads are cut at the cap; nginx Range support makes retries resumable) — recorded as a confirmation, not a defect. All 12 small requests in cycle 1 (6 post-swap + 6 during drain) returned B2 with 0 failures.
- **SIGHUP fallback: PASS.** Single `HiddenServicePort` line rewritten from `b1.sock` to `b2.sock` + SIGHUP: tor logged "Received reload signal (hup). Reloading config." and requests returned **B2 within ~2 s**, same onion address (no new identity, no descriptor re-publication as a new service).
- **A restart-to-reachable: 37 s** (fresh host-tor start, direct-target torrc, until first successful fetch per `logs/gate1b-fallback.txt`) — inside the design's accepted 30–120 s republish window; client-side HSDir caching contributes an unknown share in this sandbox.

## Gate 3 — Firewall gate mechanics — **PASS** (miniature; one recorded substitution)
Method per A8: golden table loaded into a scratch netns, both sides listed as JSON with the same nft binary (v1.0.9), canonicalised (handles/indexes/metainfo stripped, rule order preserved, set/flag order sorted) and compared (`scripts/gate3-test.sh`, `scripts/nft_compare.py`, `configs/nft-golden.nft`).
- Named-netns tooling is blocked here exactly as expected: `ip netns add` → "setns: Operation not permitted", `ip netns exec` fails the same way (log: `logs/gate3-ipnetns.txt`). The scratch namespace was therefore created with **`unshare -n`**, which works — a creation-path substitution, not a method change: the table still lives in its own throwaway netns and the host's live ruleset is never touched.
- **(a) Corruption detected: PASS.** Golden + one inserted rule (`tcp dport 22 accept`) in the "live" scratch netns → comparison reports **DIFFERENT** (exit 1).
- **(b) Formatting independence: PASS.** A semantically identical ruleset with different layout, comments, chain formatting, and reversed set/flag ordering → comparison reports **SAME** (exit 0). The gate does not depend on `nft list` text formatting, so an nftables upgrade changing output style cannot false-alarm it (Y11's failure mode) as long as both sides use the same binary — which the method guarantees.
- Recorded miniature limits: this sandbox's scratch netns cannot load `ct state` rules (nft_ct/conntrack unavailable — "Could not process rule"), so the test table uses stateless rules; the comparison method is rule-content agnostic. The production table (with conntrack and identity rules) and the `nft monitor`/dpkg/engine triggers remain Stage 1 items. (Logs: `logs/gate3-test.txt`, `logs/gate3-{ref,alt,corrupt}.json`.)

## Gate H — Headers over Tor — **PASS**
Method: `bundle-web-headers` = tranche-1 web bundle + Debian's packaged `libnginx-mod-http-headers-more-filter` (apt-fetched .deb, extracted module — the A6 "nothing compiled" approach), nginx config with `more_clear_headers Date` and explicit `Cache-Control: public, max-age=60`; page mtimes set by `scripts/publisher_mtime.py` (`FIXED_EPOCH 1577836800 + sha256(content) mod 10^8`). Fetched over Tor (host-tor substitution) via the client tor. Evidence: `logs/gateh-test.txt` (on-disk log), `logs/gateh-revalidation2.txt`, `logs/gateh-evidence.txt`.
- **No wall-clock metadata: PASS.** v1 fetch over Tor: `200`, `Last-Modified: Fri, 11 Mar 2022 11:42:13 GMT`, `ETag: "622b3595-56"` — the LM instant and the ETag mtime component are exactly the publisher-derived epoch **1646998933** for the file's sha256 (`09399994…`), not the edit time (file was created minutes earlier, Oct 2026). **`Date` header: ABSENT.** `Cache-Control` present as configured.
- **Revalidation works: PASS.** `If-None-Match` with the served ETag → **304**; `If-Modified-Since` with the served LM → **304**.
- **Edit → validators track content: PASS.** Content edited to v2 → new sha → new publisher epoch **1583592031**. After restarting B (see next bullet), a conditional request carrying the OLD ETag returned **200** with `Last-Modified: Sat, 07 Mar 2020 14:40:31 GMT` and `ETag: "5e63b25f-56"` (mtime hex = 1583592031), still no `Date`. Validators are purely content-derived in both directions.
- **Two operational findings (recorded, both consistent with the design):** (1) A running B does **not** see host-side edits to its rootfs files (the gofer file view is fixed at sandbox start; the edited file still served its old validators until restart). Production publishing is by rotation (Gate 1b) rather than live edit, so this confirms the model rather than breaking it — but any future "hot patch" idea is dead on this evidence. (2) After a hard kill, B's host socket file persists in the shared directory and a same-name rebind fails ("Address already in use") until the stale file is removed — another concrete reason the production design gives each B instance its own socket name (`b1.sock`/`b2.sock`) behind the symlink.
- Script note: `logs/gateh-test.txt` is complete — the script ran through the edit step and ended at 15:25:09 by killing its own A process (the TERM in A's log is that final step, not an external teardown). Its immediate post-edit conditional fetch returned **304 with the old validators**, which is the direct evidence for finding (1) above; the v2 result was then confirmed interactively after restarting B.

## Gate 5 — PoW under load — **ENVIRONMENT-DEFERRED** (baseline measured; engagement not demonstrable here)

- Verdict: the A13/DQ3 calibration (`PoWQueueRate ≈ 2× measured sustained rate`) **cannot be performed in this environment** and is deferred to the Stage 1 rig, where A's gVisor egress also becomes testable. Nothing in this gate contradicts the defaults; it simply cannot exercise them.

### Gate R (DESIGN-v3 A3, Y12) — DECIDED
Test LUKS2 volume on a loop device, passphrase A = "testphrase-one-123".

- **Default `luksOpen`**: `dmsetup table --showkeys` prints `crypt aes-xts-plain64:64:logon:cryptsetup:<uuid>-d0` — a kernel **keyring reference, not the raw key** (evidence: `logs/rig/gater-dmtable.txt`). Y12's suspicion confirmed: no raw master key from the dm table under default options.
- The logon key in /proc/keys is **not extractable**: `keyctl pipe` as root → "Permission denied" (logon keys are non-readable by design). `luksAddKey` without the old passphrase and without the volume key fails ("No key available with this passphrase").
- **With `luksOpen --disable-keyring`**: `dmsetup table --showkeys` prints the raw 64-byte volume key in hex (evidence: `logs/rig/gater-dmtable-nokring.txt`). Using it, `cryptsetup luksAddKey --volume-key-file volkey.bin <dev> pass2.txt` (new passphrase supplied as the positional key file) succeeded with NO old passphrase; luksDump showed keyslots 0+1, and the new passphrase was verified to open the volume.
  ⚠️ Pitfall: passing the new passphrase via `--key-file` alongside `--volume-key-file` hangs indefinitely on a hidden interactive prompt (one run killed after ~3.5 min). Use the positional form.
- **VERDICT STATEMENT: While the system is running and unlocked, a new passphrase CAN be added without the old one — YES, but ONLY if the volume was originally opened with `--disable-keyring`. Under a default open: NO.**
  Design consequence for A3: the lost-paper recovery promise is keepable, but only if the production initramfs opens the root volume with keyring disabled — a deliberate trade: the raw volume key then sits in the dm table readable by root (a one-time root compromise becomes persistent across passphrase changes until a reencrypt). That trade must be written into A3 explicitly rather than discovered later.

### A-in-gVisor egress (Gate 1 completion) — PASS
Tor (container A) running under runsc reached **Bootstrapped 100%**, established intro points, and uploaded its descriptor ("HS descriptor stored successfully", status 200, repeated). A fresh client tor then fetched the PoC page from B **end-to-end over the real Tor network — HTTP 200**, B being nginx in a `--network=none` runsc sandbox. No host-tor substitution this time. Two configuration facts were forced by experiment, both design-relevant:

1. **The OCI spec must NOT request its own network namespace for A.** With a fresh netns in the spec + `--network=host`, the sentry's outbound connects hang forever and its listeners are unreachable — silently. With the netns entry stripped from the spec and `--network=host`, gVisor egress works immediately (verified with the bundled curl diagnostic before tor was restarted).
2. **A needs `--host-uds=all`, not just `create`.** With default UDS settings, A's tor logged `connect() to socket failed: Connection refused` when opening streams to B's socket — while B's socket existed and answered host-side fetches the whole time. `create` lets a sandbox *publish* a socket (that's B); *connecting* to one inside a gofer mount needs `all`. Golden flags diverge per container: B `--host-uds=create`, A `--host-uds=all`.
   Also observed: clients holding a stale descriptor across an A restart fail fetches for minutes (dead intro points) — consistent with the accepted 30–120 s republish outage; a fresh client fetched successfully once A's new descriptor was uploaded.

### Podman shoot-out (DESIGN-v3 A5 data clause) — ROOTFUL CONFIRMED
- **Rootful podman + runsc, B with `--network=none`: PASS.** The Stage 0 setns block is gone on the rig; the container runs and nginx starts. Socket host-visibility: **fails** with a plain runsc runtime and with a `runsc.uds=all` OCI annotation (both silently serve nothing to the host); **works** via a tiny wrapper runtime (`/usr/local/bin/runsc-wrap` = `runsc --host-uds=all "$@"`) registered as a podman runtime — page served through podman, HTTP 200. Production Quadlet units must therefore use the wrapper runtime (podman runtime entries take no args of their own). One wrinkle seen live: starting a second nginx against the same socket dir fails "Address already in use" — the rotation drain discipline in the design is what prevents this in production.
- **Memory ceiling (rootful): PASS.** `--memory=128m` + shell string-doubling hog → container OOM-killed (rc 137) after the string passed 33 MB and tried to double past the limit. Ceiling genuinely enforced; no `--ignore-cgroups` needed rootful.
- **Fork bomb / pids (rootful): CONTAINED, with a caveat.** Under crun (control), `--pids-limit=32` behaves classically: the bomb fills the budget, "Cannot fork", container contained. Under runsc, burst forking makes the container's shell exit almost immediately (rc 2, no message) — at `--pids-limit` 32 and 512 alike — while spaced spawns (0.2 s apart) work fine (10/10). So a fork bomb under runsc **self-terminates before it can threaten the host** (host load stayed ≈0.5 throughout): containment yes, but the mechanism is gVisor's burst-fork fragility, not the numeric ceiling, and burst-y legitimate workloads would trip the same behaviour. Recorded as a behaviour difference to design around, not a blocker.
- **Rootless: FAIL as the engine (as exercised).** Fresh user + linger + user containers.conf: `podman run --runtime=runsc` dies at creation — "systemd error: Interactive authentication required" (no logind session in this headless context). It only runs with a `--ignore-cgroups` wrapper — then it works (container up, socket host-visible, page HTTP 200) — but with cgroups ignored, the A5 ceilings this comparison exists to verify are off the table (memory enforcement under that flag not demonstrated; the flag's documented purpose is to skip cgroup setup). This is exactly the delta review's DQ2 failure mode.
- **A5 verdict: the data says ROOTFUL.** Rootful passed serving + memory ceiling + fork containment; rootless failed to start without surrendering the ceilings. The DESIGN-v2/A5 rootful default stands, now evidence-backed rather than argued.

### Gate 5 baseline (rig) — PASS (baseline only)
`scripts/gate5-rig.sh`, 16 parallel workers × 60 s against the rig onion (each request a fresh rendezvous via a local client tor): **134 requests, 134 OK, 0 fail → 2.23 req/s sustained**, ~7 s average per-fetch latency at that parallelism. Note this is *lower* than Stage 0's sandbox figure (7.66 req/s) despite the bigger machine — the two numbers measure different bottlenecks (Stage 0's client and host-tor A shared one sandbox network path; the rig run crosses the real Tor network with A inside gVisor, at full 3-hop + rendezvous latency from a single client location). PoW engagement: not triggered at this rate and not separately provoked — unmeasured, not claimed. The A13/DQ3 queue-rate calibration still wants a dedicated multi-client run later; nothing here contradicts the defaults.

## SLICE 6 GATE ROUND — DYNAMIC FEASIBILITY (2026-10-13)

**Venue:** Muse's sandbox VM (Stage-0 pattern: standalone OCI bundles under the official `runsc` release-20251006.0, sha512-verified; the GCP rig was unreachable — sandbox→rig SSH still reset by the egress proxy — so rig-grade items are marked deferred). Rootfs: Debian 13 trixie built locally from the pinned snapshot **20251011T143150Z** (signature verified), 225-package closure, 337 MB: MariaDB 11.8.3, PHP 8.4.11 (fpm + mysql/gd/mbstring/xml/intl/zip/curl), nginx 1.26.3. All sandboxes `--network=none` under gVisor; the only outside path is a host curl to the nginx edge unix socket. Sandbox hazards encountered: the cell was recycled mid-round (all sandboxes died; state rebuilt from disk) and a neighbouring project's builds shared the 2 cores — timings are under-contention figures. Scripts/configs/logs: `poc/dynamic/` (scripts/, configs/, logs/, rust-app/).

### Gate P1 — MariaDB under gVisor: **PASS**
- **Minimal MariaDB config set for gVisor: no gVisor-specific deltas at all.** Near-stock config (skip-networking, socket-only, buffer pool 128M). io_uring probes fail with ENOSYS and InnoDB's native AIO fails — MariaDB falls back automatically (`innodb_use_native_aio=OFF`), zero `[ERROR]` lines. `O_TMPFILE` unsupported → auto-disabled. Optionally preset `innodb_use_native_aio=0` to silence probing; functionally unnecessary.
- First boot incl. `mariadb-install-db`: **23.3 s** to first query; warm restart **1.29 s**.
- Workload (InnoDB, socket): bulk transactional insert 5,000 rows **348 ms ≈ 14,400 rows/s**; 500 autocommit single-row inserts **12.3 s ≈ 41 commits/s**; create-table 264 ms; aggregate select 56 ms; update-1000 86 ms.
- **Contrast** (same rootfs, plain chroot on the host kernel; runc unavailable in this venue): bulk 457 ms; autocommit ≈ 45 commits/s. The ~25 ms/commit floor is this venue's storage, not a gVisor tax (~10%, within noise). Autocommit rate on real SSD is a rig re-check.
- **Persistence PASS** (stop/start → 500/500 rows intact, volume dir holds normal MariaDB files). **Isolation PASS** (in-sandbox /proc/net/dev = lo only).
- Venue delta (not a gVisor delta): service-uid setuid/setgid is EPERM in this nested sandbox, so the PoC ran mariadbd as root. Production runs it as `mysql` under podman+userns, which v1 already proves.

### Gate P2 — PHP-FPM under gVisor: **PASS-WITH-CONFIG**
- Proven chain: host → nginx edge socket → nginx → (fastcgi UDS) PHP-FPM → (UDS) MariaDB. Test page returned PHP 8.4.11 + session id + CRUD roundtrip OK; second request with the cookie read the session back with the counter incremented. Session + CRUD verified repeatedly.
- **Host-uds rule re-confirmed experimentally** (matches the Stage-1 rig finding for container A): a sandbox that *publishes* a socket needs `--host-uds=create`; a sandbox that *connects* to another sandbox's socket needs `--host-uds=all`. With `create`, connectors get silent Connection-refused.
- **Transport finding (sibling topology, this venue):** sandbox→sandbox UDS streams through gofer-hosted socket files corrupt/stall once a response exceeds a few KB (size ladder through fastcgi: 1 KB OK; 4–16 KB → 502 with an FIONREAD ioctl alert in nginx; 32–48 KB → HTTP 200 with 0 bytes). Control: a static 48 KB file served by nginx alone = perfect. Host↔sandbox and intra-sandbox paths are solid; the broken hop is specifically the cross-sandbox gofer hop in this nested venue. Under systrap, FPM also showed intermittent accept/read stalls (slowlog empty — stalls were outside PHP execution); ptrace was cleaner in batches. Not settled as a gVisor defect vs nested-venue artefact — and moot under the combined layout below.
- **Combined layout (one sandbox: mariadbd + php-fpm + nginx; service sockets sandbox-internal; only the edge socket shared): clean on systrap.** The exact sizes that broke cross-sandbox (4 KB, 48 KB) pass in full; CRUD + sessions clean. This sandbox then carried the entire P3 battery: the current generation's nginx log shows 65 requests — 48×200, 4×302 (logins) — with every non-200 traceable to test methodology (SMF token experiments, one proxy_pass syntax bug of mine), zero transport stalls.
- Venue deltas (same EPERM class as P1; production keeps service users): FPM pool runs as root with `php-fpm -R`; FPM socket `listen.mode=0666` instead of chown; nginx `user root;`.
- Operational recurrence: after a SIGKILL stop, a stale socket file in the shared dir blocks rebind until removed (same as Stage-0 Gate H finding #2; seen again with the Rust sandbox).

### Gate P3 — SMF 2.1.7 end-to-end: **PASS**
- **Source:** the official `download.simplemachines.org` returned 403 from this sandbox (recorded, not retried). Used the GitHub release source archive of tag **v2.1.7** (commit `d49255b955cbeeb3a702d77009c85aae517ed1e4`), sha256 `5efdadf64d91082f59176c983af26dc0e6e3dff50b5d0b1d2eeb60300b3d257d`; `index.php` defines `SMF_VERSION '2.1.7'`; `other/` installer files promoted to root per the official package layout. Checksum-verification against the official package remains a plumbing-slice item (venue-blocked here, not a product gap).
- **Install:** the real web installer, driven over the socket: database population **73 tables / 907 rows**; admin created; forum live as guest (board index 200). After install, `install.php` + SQL files deleted (production-correct).
- **KEY FINDING — REMOTE_ADDR:** admin creation first died fatally: SMF validates the registering member's IP and nginx passes the literal `unix:` for socket clients. Fix, now in both nginx configs: `fastcgi_param REMOTE_ADDR 127.0.0.1;` — principled, not a hack: over Tor there is no client IP to pass, and apps must never see real visitor IPs by design. Expect this to matter for most PHP apps (anything that logs/validates IPs).
- **Interactive battery (all through the edge socket, real web forms):** admin login ✓ (incl. admin-area password re-elevation); member `member1` created via the admin registration form ✓; member login ✓; **topic posted** in General Discussion ("Hello from the sealed forum", topic 2, by member1) ✓; **reply posted** ✓; **guest fetch of the topic page shows subject + both posts** ✓.
- Scripted-client lessons (browser users unaffected): SMF's tokens are single-use and bound to the User-Agent; with `databaseSession_loose=1` the session row flushes lazily, so a form's tokens validate only after a second request has cycled the session — a two-request curl flow fails with "session verification failed" / "token verification failed" until the form page is fetched twice. Worth knowing for any future automated testing of the tier.
- **SMF denied-needs list** (things SMF wants that the sealed world denies — all tolerated, none fatal):
  1. **Outbound mail — impossible, by design and by absence.** `mail_type=0` (PHP `mail()`), no sendmail/MTA binary exists anywhere in the rootfs. Registration activations, notifications, password reminders, birthday mails (11 scheduled tasks exist) can never leave. Apps must run with mail expectations off; the tier should say so in-product.
  2. **Server-side update/version checks — fail, logged, recurring.** The installer and later normal use both logged `Could not retrieve the file https://www.simplemachines.org/smf/current-version.js?version=SMF+2.1.7` in `smf_log_errors` (2 occurrences). The installer's welcome page likewise showed its "install script is out of date" warning with the current version unknown. Non-fatal noise; error-log hygiene item for the tier.
  3. **Remote avatars — downloaded server-side by default** (`avatar_download_png=1`): setting an avatar by URL makes the server fetch it → fails sealed (and would be an egress hole if it worked). Gravatar-style flows have the same shape.
  4. **Server-side image proxy** (`proxy.php`): posted external images are fetched/cached by the server → they break sealed; the visitor's browser never gets the origin either (privacy-preserving outcome, functionality cost).
  5. **Registration statistics phone-home** at install (fsockopen to simplemachines.org) — skipped in our run because boardurl was `localhost`; would fail sealed in production-shaped installs. Non-fatal.
  6. **Wall-clock dependence:** SMF timestamps everything from server time (posts, sessions, scheduled tasks). Expected; the host's NTS-disciplined clock is the tier's answer, recorded as a fact, not a defect.
  7. Install-time writable-check + DB-backed sessions + token machinery all work sealed; no other egress was attempted during the full battery (final `smf_log_errors` contained only the version-check entries).

### Gate P4 — Rust service (A22, language-neutral app slot): **PASS** (glibc build; musl-static form venue-blocked, see below)
- Service: axum 0.8 / tokio (standard epoll, **not** tokio-uring) + rusqlite with bundled SQLite, written for this gate (`poc/dynamic/rust-app/`). Endpoints: `/` status JSON, `/set`, `/get` (KV over SQLite).
- **UDS serving ✓** — listens on a unix socket in the shared sealed dir (`--host-uds=create`); full write+read roundtrip direct from the host over the socket.
- **nginx proxying ✓** — the app sandbox's nginx proxies `/rust/` → the Rust socket (app sandbox at `--host-uds=all`); set+get through the proxy verified, forum simultaneously 200 on the same nginx. (Syntax note for the plumbing slice: `proxy_pass http://unix:/path.sock:/;` — the colon before the URI matters; a slash makes nginx treat it as part of the socket path and 502s.)
- **SQLite persistence ✓** — DB file on the data volume; cold restart → value intact; **time-to-first-answer after cold restart 0.28 s** (sandbox + process + SQLite open).
- **Isolation ✓** (lo only). **gVisor syscall friction: none observed** — tokio/epoll + UDS + SQLite ran clean under systrap; no errors in console or runsc logs. Sandbox RSS ≈ 10 MB gofer + process (vs ~96 MB sentry for the whole PHP/MariaDB/nginx combined sandbox).
- **Binary: 3,947,208 bytes** (gnu target, dynamically linked to glibc; ran in a Debian-rootfs bundle). 
- **Musl-static form: NOT completed in this venue, for venue reasons only.** rustup's `x86_64-unknown-linux-musl` target + toolchain are installed and the gnu build works. The C compiler for the bundled SQLite was the blocker: the host's apt is locked by a stuck runtime-maintenance replay (not ours to kill), the sandbox egress proxy 404s the Ubuntu pool, and the musl.cc standalone toolchain — downloaded complete and tar-verified — ships a **32-bit gcc that segfaults** under this nested sandbox. None of these exist on the rig or a normal host; building the static binary there is a plumbing-slice checkbox, not an open design question. The design consequence stands regardless and is the point of the gate: **the app slot is language-neutral (app process + socket + data volume). PHP-FPM is runtime #1; a native binary is runtime #2** — and in its static form it needs no interpreter stack, no DB server, and a rootfs that is literally the binary alone (staging script `scripts/stage-rust.sh` already encodes that shape).

### Recommended shape for the Slice 6 plumbing build
**One combined app container** — nginx + runtime (PHP-FPM and/or a native process) + MariaDB as processes in a single gVisor sandbox; service sockets sandbox-internal; only the edge socket is shared with container A. Argued from this round's evidence:
1. Every cross-sandbox socket hop in this venue was either flag-sensitive (host-uds publisher/connector asymmetry, P2) or data-corrupting at size (the >4 KB gofer finding, P2). Intra-sandbox UDS was flawless at every size and carried the whole P3 battery.
2. Production B is already a single container in v1 — the combined shape changes nothing in the shipped topology, Quadlet wiring, or the nft/firewall story. Sibling DB/app containers would be a new topology bought with the flakiest mechanism measured this round.
3. The language-neutral slot drops out naturally: the app container's init starts nginx + the chosen runtime process(es); PHP-FPM and a native binary were both proven behind the same nginx/edge wiring, including simultaneously.
Per-process separation inside the sandbox (distinct users, as production already does) stays; splitting databases into sibling *containers* can be re-tested on the rig, where podman + real volumes replace the gofer path, if a future need argues for it.
