# Boot-Chain Review #2 — Verdict A with the argon2id correction
## Received from Cameron 2026-10-11 (pasted in chat; second independent review of BOOT-CHAIN-PACK-for-claude-opus.md; Review #1 is the basis of A19). Saved in condensed-but-faithful form; load-bearing passages near-verbatim.

**Verdict: A — with one correction that makes it strictly simpler and no weaker.** Retain encrypted /boot, add PBKDF2 access for each generated phrase that must work at GRUB, use a separate random keyfile for the initramfs — and **drop the argon2id keyslots entirely.** Layout: PBKDF2 slot (MAIN), PBKDF2 slot (SPARE), one keyfile slot. “The ‘dual-derivation’ half of Option A buys you nothing, and actively costs you re-key reliability.”

**B is a constraint violation dressed as a proposal**: it trades away the headline seal-when-off guarantee for exactly the userbase that self-selects into running a Tor onion service.

**The real single point of failure is the entropy source, not the KDF.** Audit: generator uses a CSPRNG (`getrandom()`, blocking until seeded — fresh installs on minimal hardware are entropy-starved at exactly the wrong moment), wordlist is the full ~7776 unique entries, selection has no modulo bias. If that's sound the KDF is a non-issue; if not, no KDF saves you.

**Q1 — PBKDF2 at ~90 bits: no material weakening, and it generalises.** A slow/memory-hard KDF compensates for *missing* entropy. A uniform 90-bit secret has none missing: 2^90 ≈ 1.2×10^27; at a generous 10^12 guesses/sec against a zero-stretch hash ≈ 38M years. **A LUKS volume's offline resistance is the MINIMUM over its keyslots** — the attacker attacks the cheapest slot and ignores argon2id. “If you trust 90 bits, PBKDF2 is fine and argon2id is pointless; if you don't trust 90 bits and want argon2id's margin, the coexisting PBKDF2 slot throws that margin away. There is no configuration where the argon2id slot earns its place.” GRUB iterations: set as high as boot UX tolerates anyway (free insurance against the entropy estimate being wrong), but it isn't an attacker-speed estimate. **SPARE must also be PBKDF2** — an argon2id spare reproduces the original bug “discoverable only on the worst possible day.” Two 90-bit secrets ≈ ≤1 bit margin cost; the spare's real risk is physical (paper in a drawer).

**Q2 — Keyfile leaks, likeliest first:** (1) backups/disk images — any /boot copy to unencrypted media carries the keyfile in plaintext inside the initramfs; (2) initramfs regeneration — fine only if /tmp, /var/tmp AND SWAP are encrypted; **swap is the sharp edge** (can page out keyfile, volume key, or phrase) → random-key swap or none, no hibernation; (3) the ISO — a baked-in keyfile = identical key on every install = catastrophic → per-install CSPRNG generation, ≥256-bit, never shipped; (4) installer logs — Calamares can echo luksAddKey invocations/secrets → scrub /var/log/Calamares.log, verify no phrase/keyfile in /var/log; (5) tooling residue — initrd.img-*.old, dkms/dpkg copies, etckeeper versioning /etc; (6) crash dumps — kdump to an unencrypted target captures it → disable or encrypted target only. **Hygiene:** keyfile per-install CSPRNG, mode **0400 root:root**, on encrypted root; `UMASK=0077` in initramfs.conf (Debian's historical 0644 would expose it); encrypted-or-no swap; kdump off/encrypted; shipped backup tooling **excludes /boot and initramfs by default and encrypts output — enforced by the OS, not documentation**; idempotent initramfs hook; don't let .old images accumulate outside encrypted /boot. Note: the keyfile-in-initramfs IS Debian's standard documented method for one-prompt encrypted-/boot; a reliable GRUB→kernel keyring handoff is NOT available on the initramfs-tools stack — design assuming the keyfile ships, and contain it.

**Q3 — GRUB behaviour:** steer by slot COMPOSITION, not priority (GRUB iterates slots, generally ignores LUKS2 priority). PBKDF2-only passphrase slots = nothing for GRUB to get wrong; mixed slots invite build-varying stall/fall-through behaviour. Point initramfs explicitly at the keyfile slot via crypttab. Maintenance/reencrypt: `cryptsetup reencrypt` re-wraps existing keyslots under the new volume key automatically; phrase and keyfile keep working; regenerate initramfs and **boot-test GRUB unlock before declaring the re-key done**.

**Q4 — Option B evil-maid:** mid-tier risk directly contradicting the headline claim (the tamper happens while OFF — exactly the covered state; realistic adversaries for this userbase: abusive cohabitant, roommate, border/landlord). Cheap mitigations all fail within constraints: TPM auto-unlock breaks seal-when-off; TPM warn-only drowns in false positives on every kernel update; signed UKI needs MOK (barred); post-boot checksums are retroactive. Clean closure = keep /boot encrypted.

**Q5 — A18 interaction:** mechanism unaffected (volume-key slot-adding works regardless). A18's raw-volume-key exposure strictly dominates the keyfile's running-system exposure. The decisive interaction is re-key reliability: **dual slots create two silent partial-update failure modes** (update argon2id only → new phrase rejected at GRUB, old still boots; update PBKDF2 only → revoked old phrase still unlocks via argon2id indefinitely). PBKDF2-only deletes the failure class. Reference re-key sequence (volume key from `dmsetup table --showkeys` field 5, protected temp files with shred trap): extract VK → stage new phrase → `luksAddKey --volume-key-file VK --pbkdf pbkdf2` → `open --test-passphrase` → `luksKillSlot` old → `update-initramfs -u`. **Add → test → kill → regen**, destructive step last; force a reboot/GRUB test before the machine is considered re-keyed. Spare goes through the identical PBKDF2 path.

**Q6 — Ship the corrected A**: encrypted /boot, PBKDF2-only phrase slots, one per-install CSPRNG keyfile, argon2id nowhere. **Feared failure story: a well-meaning backup ships the disk key in plaintext** (owner or a future “export your site” feature copies a filesystem image or /boot to USB/cloud; the keyfile rides inside the initramfs; “sealed when off” silently false; headline: *“Privacy OS backed up its own disk key in plaintext”*). Hence the backup rule must be OS-enforced; and if Debian ever offers a reliable keyring handoff, dropping the keyfile is the first v2 move. **Parked for later (explicitly not v1): detached LUKS header on removable media** (“seal-when-off++” — no header on disk = no slots to attack) as an advanced opt-in; barred from v1 by the no-new-concepts constraint.
